# 브라우저 통합 검증 절차와 기록 양식

이 문서는 브라우저 검증의 두 방법을 설명합니다.

- 0장: Playwright 자동 브라우저 검증. 렌더링·Pointer Lock·조준·명중·점수·재장전·일시 정지·다시 시작·실제 60초 종료를 확인합니다.
- 1~7장: 사람이 데스크톱 브라우저에서 직접 플레이하는 수동 절차와 빈 기록 양식. 효과음 청취와 실제 마우스 조작감(4장)은 사람만 확인할 수 있습니다. 3장의 시나리오는 자동 검증이 실패했거나 다른 브라우저에서 재현할 때 사용합니다.

자동 규칙 테스트(`node --test`)는 `docs/js/rules.mjs`만 검사하며 브라우저를 실행하지 않습니다.

## 0. 자동 브라우저 검증(Playwright)

### 0.1 준비와 실행

저장소 루트에서 실행합니다. Node.js 22 이상, Python 3, 인터넷 연결이 필요합니다.

```sh
npm ci
npx playwright install chromium
npm run test:browser
```

- 예상 결과: 3개 시나리오가 모두 `✓`로 표시되고 명령이 종료 코드 0으로 끝납니다. 실행 시간은 약 2분입니다.
- 검토용 대표 증거를 저장소에 남길 때: `EVIDENCE_DIR=tests/browser/evidence npm run test:browser`.
- 포트 8123이 사용 중일 때: `GUN_SHOOTER_PORT=8130 npm run test:browser`.

### 0.2 자동 검증이 근거로 인정하는 것

다음 방법으로 얻은 결과는 실제 브라우저 통과 증거입니다.

- Playwright의 마우스·키보드 입력. 브라우저 입력 경로(CDP `Input` 이벤트)로 전달되며, 게임은 사람이 입력할 때와 같은 `mousemove`(`movementX/Y`)·`mousedown`·`keydown` 처리기로 받습니다.
- 시작·계속하기·다시 시작 버튼 클릭으로 얻은 실제 Pointer Lock. 테스트는 `document.pointerLockElement`가 `#scene` 캔버스인지 확인합니다.
- 헤드리스 Chromium의 SwiftShader WebGL로 그린 실제 화면의 스크린샷 분석(하늘·바닥 밝기 차이, 총기 영역 픽셀, 빨간 표적 고리 위치, 조준 전후 장면 차이).
- HUD·패널 DOM 텍스트와 Node 단조 시계(`performance.now()`)로 기록한 실제 시간 흐름.
- 페이지 안의 읽기 전용 관측기(`installObserver`)가 페이지의 `performance.now()`로 기록한 전환 시각. 관측기는 게임 모듈보다 먼저 `pointerlockchange`·`keydown`·`mousedown` 수신기를 등록하고, `MutationObserver`로 패널 표시·탄약·상태 문구·재장전 막대의 DOM 전환을 기록합니다. 이벤트를 막거나 게임 상태를 바꾸지 않고 별도 전역(`window.__gsObs`)에만 씁니다. 게임도 같은 `performance.now()` 시계를 쓰므로 다음 판정이 폴링 간격·시작 클릭·잠금 재시도 지연과 섞이지 않습니다.
  - 활성 라운드 시간: 실제 잠금 획득(`lock`)부터 종료 패널(`panel-end`) 표시까지 60000 ms 이상이어야 하며, 그 사이에 잠금 해제·재잠금·다른 패널 표시가 없어야 합니다. CPU 렌더링의 프레임 지연은 63000 ms 미만까지 허용합니다.
  - 재장전: `R` 키 도착부터 탄약 `12 / 12` 전환과 재장전 막대 제거까지 1400 ms 이상, 2400 ms 미만이어야 합니다. 재장전 중 실제 클릭이 막대 표시 뒤에 도착했고 그 사이 탄약 표시가 바뀌지 않았는지 함께 확인합니다. 빈 탄창(`0 / 12`)과 탄약이 남은 상태(`11 / 12`) 두 경우를 검사하므로 빈 탄창 차단만으로는 통과하지 않습니다.

테스트는 게임 상태·카메라·타이머·`roundMs`·`performance.now`를 바꾸지 않고, `fire`·`startRound` 등 게임 함수를 호출하지 않습니다. 페이지 안에서는 읽기 전용 관측(DOM 텍스트, `requestAnimationFrame` 대기, 별도 OffscreenCanvas의 스크린샷 디코딩, 위 관측기)만 합니다.

표적 조준 방법: 정면 시점의 스크린샷 한 장에서 흔들리지 않는 표적 자리(`SLOTS` 중 `sway: 0`) 위치에 빨간 고리가 보이는 자리를 고릅니다. 그 자리 중심으로 향하는 각도를 마우스 이동량(감도 0.0022 rad/px)으로 바꾸어 실제 마우스를 움직입니다. 명중은 HUD 점수가 정확히 100 늘어난 것으로 판정합니다.

### 0.3 근거로 인정하지 않는 것

다음 방법으로 얻은 결과는 통과 증거가 아닙니다. 사용했다면 해당 항목을 미실행으로 두고 참고 사항에만 적습니다.

- `dispatchEvent` 등으로 페이지 안에서 만든 합성 마우스·키보드 이벤트
- 모의 Pointer Lock API
- 게임 상태나 규칙 설정(`roundMs`, `reloadMs` 등)을 직접 바꾸는 것, 게임 함수를 직접 호출하는 것
- 타이머 단축, 시계 조작, 코드 수정, 로컬 오버라이드로 시간을 줄이는 것
- 스크린샷만으로 시간 흐름이나 입력 동작을 주장하는 것(시간은 단조 시계와 HUD 기록으로, 입력은 HUD 변화로 확인합니다)

CPU 렌더링(SwiftShader)의 프레임 속도는 실제 기기 성능의 근거가 아닙니다.

### 0.4 헤드리스 Chromium에서 관측한 제약

- `chrome-headless-shell`(Playwright 기본 헤드리스 빌드)은 Pointer Lock 중 마우스 이동 하나를 `movementX/Y = 절대 좌표` 이벤트와 `(0,0)`으로 돌아오는 음수 이벤트의 쌍으로 보냅니다. 이동량이 서로 상쇄되어 조준을 검증할 수 없습니다. 그래서 설정은 전체 Chromium의 new headless(`channel: 'chromium'`)를 사용합니다. 이 빌드는 `steps: 4`로 120px 이동할 때 `movementX = 30`을 네 번 보냅니다.
- 헤드리스 Chromium에서 Playwright의 `Escape` 키 입력은 Pointer Lock을 해제하지 않습니다(브라우저 UI가 처리하는 키이기 때문입니다). 테스트는 먼저 `Escape`를 보내고 해제 여부를 `escKeyReleasedLock`으로 기록합니다. 해제되지 않으면 `document.exitPointerLock()`으로 잠금을 해제하고 `releasedVia`에 그 사실을 적습니다. 이 경우 일시 정지 화면·시간 정지·계속하기·다시 시작은 검증되지만 **`Esc` 키 자체의 잠금 해제는 미검증**입니다. 사람이 3장 B8로 확인합니다.
- 잠금 해제 직후 재잠금 거부: 테스트는 버튼 클릭 뒤 3초 안에 잠금이 없으면 단계 기록을 남기고 1.5초 기다린 뒤 다시 누릅니다(최대 3회, 7장의 대기 후 재시도 절차와 같음). `document.exitPointerLock()`으로 해제한 경우에는 거부가 관측되지 않았습니다(`attempt: 1`).
- 잠금 요소는 `pointerlockchange` 처리기보다 먼저 정해집니다. 테스트는 잠금과 오버레이 닫힘을 함께 기다린 뒤 HUD를 읽습니다.
- Chromium은 `/favicon.ico`를 요청합니다. `docs/index.html`의 `<link rel="icon" href="data:,">`가 이 404 콘솔 오류를 막습니다.

### 0.5 산출물 확인

시나리오마다 `test-results/evidence/<시나리오>/`(또는 `EVIDENCE_DIR`)에 다음이 생깁니다.

- `log.json`: `revision`(HEAD SHA, `git status --short`, `docs/` diff 해시, 게임 파일 blob 해시), `environment`(Node·플랫폼·Chromium 버전·실행 인자·명령), `steps`(단계별 단조 시각 `t`(ms)와 점수·탄약·시간·상태·재장전 표시·패널 텍스트·잠금 요소), `console`, `pageErrors`, `requests`, `failedRequests`, `httpErrors`, `screenshots`, `observer`(관측기의 전환 기록, 페이지 시계 ms), `problems`(오류 검사에서 발견한 항목), 시나리오 실패 시 `failure`(오류 메시지), `result`.
- `result`는 시나리오 본문과 afterEach의 오류 검사(`pageerror`·콘솔 error/warning·요청 실패·HTTP ≥ 400·허용되지 않은 외부 요청)를 모두 평가한 뒤 저장합니다. 본문이 실패하면 Playwright 상태(`failed`·`timedOut` 등), 본문은 통과했지만 오류 검사에서 항목이 있으면 `failed`, 둘 다 없을 때만 `passed`입니다. 실패하면 `NN-failure.jpg`도 남깁니다.
- `NN-<단계>.jpg`: 초기·시작·조준·명중·재장전·정지·종료·다시 시작 화면.

`result`가 `passed`가 아니면 그 시나리오는 실패입니다. 기록 파일이 없는 시나리오는 미실행입니다.

### 0.6 실패 진단

- `Executable doesn't exist`: `npx playwright install chromium`을 다시 실행합니다.
- `console error/warning`, `requestfailed`, `HTTP >= 400`, `버전 고정 CDN 외 외부 요청`: `log.json`의 해당 배열에서 URL과 시각을 확인합니다. CDN에 연결할 수 없으면 모든 시나리오가 실패합니다.
- `정면 시점에 보이는 정지 표적이 없습니다`: 실패 스크린샷과 `aim:` 단계 기록을 확인합니다. 정지 자리 8곳이 모두 비어 있거나 조준 기준점이 어긋난 경우입니다.
- `Pointer Lock을 얻지 못했습니다`: 단계 기록의 `attempt`와 `error`(게임 오류 문구)를 확인합니다.
- 시간 관련 실패: `03-full-round`의 `활성 라운드 시간(페이지 시계)` 단계에서 `lockAtMs`·`endPanelAtMs`·`activeMs`와 `eventsBetween`(라운드 중 잠금·패널 전환)을 확인합니다. `시간 관측` 단계(1초 간격 HUD `time`과 `sinceClickMs`)는 보조 기록입니다.
- 재장전 관련 실패: `01-play-hit-miss-reload`의 `재장전 완료(…)` 단계의 `observed`(`barShownMs`·`ammoFullMs`·`barHiddenMs`·`clicksDuringReloadMs`·`ammoChangesDuring`, `R` 키 도착 기준 ms)를 확인합니다.
- 실패 화면과 오류 위치: `test-results/artifacts/<테스트>/`.

## 1. 작성 규칙

### 1.1 기록을 만들고 제출하는 방법

1. 이 파일을 저장소 작업 트리 **밖**에 복사합니다. 예: `~/gun-shooter-verification/browser-verification-<SHA 앞 12자리>-<YYYYMMDD>.md`.
   작업 트리 안에 기록이나 증거 파일을 만들면 `git status --short` 결과가 바뀌어 대상 revision과 일치하는지 판단하기 어렵습니다.
2. 증거 파일(스크린샷·영상·콘솔 로그·HAR)은 같은 폴더에 두고, 기록란에 파일 이름과 영상의 시각(예: `round1.mp4 00:42`)을 적습니다.
3. 기록 파일과 증거 폴더를 검증을 요청한 사람에게 직접 제출합니다. PR 설명 자동 수정이나 서버의 후처리를 기대하지 않습니다.

### 1.2 상태 값

| 상태 | 의미 |
| --- | --- |
| 통과 | 조작을 실제로 수행했고, 예상 결과를 모두 관측했으며, 증거 참조를 적었습니다. |
| 실패 | 조작을 수행했으나 예상 결과와 다른 점이 하나 이상 있습니다. 실제 관측란에 차이를 적습니다. |
| 미실행 | 조작을 수행하지 않았거나, 수행했어도 증거가 없습니다. |

- 상태란이 비어 있으면 **미실행**으로 취급합니다.
- 증거 참조란이 비어 있는 항목은 통과로 기록하지 않습니다.
- 일부 단계만 수행했다면 그 시나리오는 미실행 또는 실패로 적고, 수행한 범위를 실제 관측란에 씁니다.

### 1.3 증거 종류

| 기호 | 증거 | 사용하는 경우 |
| --- | --- | --- |
| S | 스크린샷 | 정지 상태(초기 화면, HUD 값, 종료 화면, 오류 문구) |
| V | 화면 녹화 영상 | 움직임·시간 흐름(마우스 조준, 파티클, 표적 쓰러짐·재등장, 재장전 시간, 60초 진행) |
| A | 소리가 함께 녹음된 영상 | 효과음. 녹음할 수 없으면 H로 기록하고 그 사실을 적습니다. |
| C | 콘솔 기록 | DevTools Console 내용을 저장한 파일 또는 전체 화면 캡처 |
| N | 네트워크 기록 | DevTools Network의 HAR 파일 또는 요청 목록 전체 캡처 |
| H | 사람 관측 메모 | 청취, 조준 감각처럼 기록 장치로 대신할 수 없는 판단. 누가 언제 확인했는지 적습니다. |

- 파티클, 마우스 조준, 표적 애니메이션, 재장전 시간은 스크린샷 한 장으로 입증하지 않습니다. 영상(V)을 사용합니다.
- 효과음은 스크린샷이나 콘솔 기록으로 입증하지 않습니다. A 또는 H로 기록합니다.

### 1.4 수동 기록에서 통과로 기록하지 않는 방법

수동 기록에는 사람이 직접 조작하고 본 결과만 적습니다. 자동 검증 결과는 0장의 산출물로 따로 제출합니다. 다음 방법으로 얻은 결과는 통과가 아닙니다. 사용했다면 해당 항목을 미실행으로 두고 참고 사항에만 적습니다.

- DevTools Console에서 `dispatchEvent` 등으로 만든 합성 마우스·키보드 이벤트
- DevTools Console에서 게임 상태나 규칙 설정(`roundMs`, `reloadMs` 등)을 직접 바꾸는 것
- 타이머 단축, 코드 수정, 로컬 오버라이드로 시간을 줄이는 것

FPS(초당 프레임 수)는 완료 기준이 아닙니다. 끊김이 눈에 띄면 참고 사항에만 적습니다.

## 2. 사전 조건 기록

검증 동안 저장소 파일을 바꾸지 않습니다. 모든 명령은 저장소 루트에서 실행합니다.

1. 터미널에서 다음을 실행하고 출력 전체를 기록합니다.

   ```sh
   git rev-parse HEAD
   git status --short
   ```

   `git status --short` 출력이 비어 있지 않으면 작업 트리에 변경이 있는 것입니다. 이 경우 출력 전체를 적고, 그 상태로 얻은 결과는 해당 SHA의 검증으로 보지 않습니다.
2. 같은 터미널에서 정적 서버를 시작하고 검증이 끝날 때까지 유지합니다.

   ```sh
   python3 -m http.server 8000
   ```

   포트 8000을 쓸 수 없으면 다른 포트를 쓰고, 실제 명령과 URL을 그대로 적습니다.
3. 브라우저 전체 버전을 확인합니다. Chrome은 `chrome://version`, Edge는 `edge://version`, Firefox는 `about:support`의 버전 값을 그대로 복사합니다.
4. 마우스가 연결된 데스크톱에서 수행하고, 소리를 들을 수 있도록 출력 장치를 켭니다. 인터넷에 연결되어 있어야 합니다(Three.js를 CDN에서 불러옵니다).

| 항목 | 기록 |
| --- | --- |
| 검증자 | |

### B8. `Esc` 정지와 계속하기

#### B8-2. 잠금 해제 직후 재잠금 거부와 재시도

#### B8-3. 게임 도중 다시 시작

- 전제 상태: 라운드 진행 중이고 마우스가 잠겨 있습니다. 남은 시간이 `50.0` 이하이고 점수가 `0`보다 큽니다.
- 증거: V (각 단계 전체), 각 재시작 직후 HUD는 S

##### B8-3a. 명중 직후 다시 시작

- 조작 순서:
  1. 표적을 맞히고, 표적이 쓰러지거나 파티클·명중 표시(빨간 X)가 남아 있는 동안(약 0.3초 안) `Esc`를 누릅니다.
  2. 점수·탄약·남은 시간을 적고 2초 이상 기다린 뒤 **다시 시작**을 실제 마우스로 한 번 클릭합니다.
  3. 잠긴 직후 HUD와 화면을 보고, 한 번 클릭해 탄약을 봅니다.
- 예상 결과:
  - 1~2: 일시 정지 패널이 보이고, 클릭하는 동안 탄약이 줄지 않고 발사음이 나지 않습니다.
  - 3: 점수 `0`, 탄약 `12 / 12`, 남은 시간 `60.0`부터 줄어듭니다. 시점이 정면으로 돌아오고, 표적 6개가 모두 다시 세워집니다(짧은 등장 애니메이션). 이전 라운드의 파티클·탄착 표시·명중 표시·총구 섬광·반동이 남지 않고 HUD 가운데 안내 문구가 비어 있습니다.
  - 3의 첫 클릭 후 탄약은 `11 / 12`입니다.

##### B8-3c. 잠금 거부 후 재시도와 계속하기

- 조작 순서:
  1. 진행 중에 점수·탄약·남은 시간을 적고 `Esc`를 누릅니다.
  2. 곧바로(`Esc` 후 1초 안) **다시 시작**을 한 번 누릅니다. 거부 문구가 보이면 그대로 적습니다.
  3. 거부되었다면 2초 이상 기다린 뒤 **계속하기**를 누릅니다.
  4. 진행 중에 다시 `Esc`를 누르고 곧바로 **다시 시작**을 누릅니다. 거부되었다면 2초 이상 기다린 뒤 **다시 시작**을 다시 누릅니다.
- 예상 결과:
  - 2: 거부되면 "마우스 잠금(Pointer Lock)에 실패했습니다"로 시작하고 "잠시 후 버튼을 다시 눌러 주세요."로 끝나는 문구가 보이고 일시 정지 화면과 두 버튼이 유지됩니다. 점수·탄약·남은 시간은 1에서 적은 값 그대로입니다. 거부되지 않고 바로 새 라운드가 시작되었다면 "거부 없음"으로 적고 3은 수행하지 않습니다.
  - 3: 오류 문구가 사라지고 기존 라운드가 1에서 적은 점수·탄약·남은 시간에서 이어집니다(초기화되지 않음).
  - 4: 재시도가 성공하면 B8-3a의 3과 같은 새 라운드가 한 번만 시작됩니다. 남은 시간은 `60.0`부터 한 번만 줄어들기 시작하고 다시 `60.0`으로 돌아가지 않습니다.

### B9. 실제 60초 종료

- 전제 상태: 새 라운드 시작 직후(남은 시간 `60.0`). 이 라운드에서는 일시 정지하지 않는 것을 권장합니다. 정지했다면 정지 구간을 적습니다.
- 조작 순서:
  1. 시작 시각을 영상 시각으로 기록하고, 남은 시간이 0이 될 때까지 평소처럼 플레이합니다.

  3. 종료 화면에서 화면을 여러 번 클릭하고 `R`을 누릅니다(**다시 시작** 버튼은 누르지 않습니다).

  - 시작 시각부터 종료 화면까지 영상 시간은 60초에 정지 구간을 더한 값과 거의 같습니다.

## 7. 문제가 생겼을 때

- 장면이 보이지 않음: Network에서 `three.module.js` 요청의 상태를 확인하고 Console 오류를 적습니다. CDN에 연결할 수 없으면 B1을 실패로 적고 이후 시나리오는 미실행으로 둡니다.
